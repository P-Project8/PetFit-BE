## 1. JWT 인증 구조

### 1.1 결정 요약 (Trade-off 표)

| 결정 항목 | 우리 선택 | 장점 | 포기한 것 |
|----------|----------|------|----------|
| Access Token 만료 | **1시간** | 탈취 시 피해 범위 제한 | 사용자가 1시간마다 갱신 필요 |
| Refresh Token 도입 | **O (7일)** | UX 유지 + 자동 갱신 | 추가 저장소 필요 |
| Refresh Token 저장 위치 | **DB** | 서버 측 강제 폐기 가능 | 매 갱신 시 DB 조회 비용 |
| Access Token 무효화 | **Redis 블랙리스트** | 로그아웃 즉시 차단 | JWT 본연의 stateless 손상 |
| 토큰 검증 캐싱 | **Redis 화이트리스트** | 매 요청 DB 조회 회피 | 캐시 일관성 관리 부담 |
| 서명 알고리즘 | **HS256** (HMAC) | 대칭키 — 빠르고 단순 | 키 노출 시 위조 가능 (단일 서비스라 OK) |
| 클라이언트 저장 위치 | **localStorage** | SPA 구현 단순 | XSS 취약 (CSP/Sanitizer 방어) |

### 1.2 결정의 근거

#### A. Access Token 만료를 1시간으로 한 이유
- **너무 짧으면 (5분 등)**: 모바일 환경에서 토큰 갱신 빈도 ↑ → UX 저하
- **너무 길면 (24시간 등)**: 탈취 시 피해 큼
- **1시간**은 업계 표준 (Google OAuth 기본값, AWS Cognito 권장값과 동일)
- 보안 사고 발생 시 평균 발견 시간(MTTD) 통계상 1시간 내 격리 어려움 → 그래도 24시간보다 24배 안전

#### B. Refresh Token DB 저장을 택한 이유
**대안**: Refresh Token도 stateless로 발급 (Self-contained JWT)
- ❌ 탈취 시 만료 전까지 폐기 불가
- ❌ 비밀번호 변경 시 기존 Refresh를 무효화할 방법 없음

**우리 선택**: DB 저장 + 사용자당 1개 보관
- ✅ 로그아웃/비밀번호 변경/보안 사고 시 즉시 폐기 가능
- ✅ 동시 로그인 제한 정책 가능 (현재는 미적용이지만 옵션)
- 비용: 매 토큰 갱신 시 DB read 1회 — 7일에 1회 정도라 무시할 수준

#### C. Access Token 블랙리스트를 Redis로 한 이유
**Stateless JWT의 본질적 한계**: 발급 후 만료 전까지 폐기 불가.

**해결책 비교:**

| 방법 | 장점 | 단점 |
|------|------|------|
| 안 함 (순수 JWT) | 단순 | 로그아웃해도 1시간 유효 ❌ |
| DB 블랙리스트 | 영구 보존 | 매 요청마다 DB 조회 — 느림 |
| **Redis 블랙리스트** | **빠름 (메모리)**, TTL 자동 만료 | Redis 다운 시 일시 무방비 |

→ **Redis** 가 합리적. TTL을 Access Token 만료 시간과 동일하게 설정해서 메모리 누수 없음.

#### D. localStorage vs httpOnly Cookie

| 저장소 | 장점 | 단점 |
|--------|------|------|
| **localStorage** (우리 선택) | 구현 단순, SPA 친화 | **XSS 취약** |
| httpOnly Cookie | XSS 안전 | **CSRF 취약**, 도메인 정책 복잡 |

**우리가 localStorage를 택한 이유**:
1. **SPA + REST 구조**: 쿠키 기반은 CORS/CSRF 설정 복잡
2. **XSS 방어 다층 적용**:
   - React의 기본 escape (innerHTML 미사용)
   - 사용자 입력 sanitize
   - CSP 헤더 (`Content-Security-Policy`) 적용 예정
3. **CSRF는 우리 환경에서 적용 불가**: REST API는 Authorization 헤더 기반 → 쿠키 자동 전송이 없음

**솔직한 한계 인정**: XSS 방어가 완벽하지 않으면 위험. 운영 단계에서 Cookie + CSRF 토큰 조합으로 강화 가능.

### 1.3 구현 위치 매핑

| 기능 | 파일 |
|------|------|
| 토큰 발급/검증 | `global/security/TokenProvider.java` |
| 인증 필터 | `global/security/JwtAuthenticationFilter.java` |
| 화이트리스트 (인증 제외 경로) | `application.yml` + `ExcludeAuthPathProperties.java` |
| 블랙리스트 | Redis (key: `blacklist:access:{token}`, TTL = 토큰 잔여 시간) |
| Refresh 저장 | DB `refresh_tokens` 테이블 |

### 1.4 면접/발표 예상 질문 & 답변

**Q. Refresh Token이 탈취되면 어떻게 되나?**
A. DB에서 즉시 폐기 가능. 사용자가 "다른 기기에서 로그아웃" 요청 시 해당 Refresh 삭제. 또한 비밀번호 변경 시 자동으로 모든 Refresh 폐기. 추가로 IP/User-Agent 기록을 통해 이상 탐지 가능 (현재는 기본 구현).

**Q. JWT는 stateless라는데 블랙리스트 쓰면 stateful 아닌가?**
A. 맞습니다. JWT의 stateless 장점을 일부 포기하고 즉시 폐기 가능성을 얻는 trade-off입니다. 100% stateless를 고수하면 로그아웃 후에도 토큰이 유효해 보안 사고에 취약하므로, 보안 우선으로 결정.

**Q. 왜 OAuth 2.0 / OIDC 안 썼나?**
A. 자체 가입/로그인이 주된 시나리오이고 SNS 로그인은 범위 외. OAuth는 제3자 인증 위임 프로토콜이라 우리 케이스에 과잉. 향후 카카오/구글 로그인 추가 시 Spring Security OAuth Client로 도입 예정.

## 2. 인프라 아키텍처 (EC2 + S3)

### 2.1 현재 구성 다이어그램

```
[사용자 브라우저]
       ↓ HTTPS (예정)
[AWS EC2 t3.small]
  ├── Nginx (80) — 정적 파일 / 리버스 프록시
  ├── Spring Boot (8080) — REST API
  ├── PostgreSQL 15 (5432) — 영속 데이터
  └── Redis 7 (6379) — 캐시 + 블랙리스트
       ↕
[AWS S3 ap-northeast-2] — 이미지 영구 저장
       ↕
[Google Gemini API] — AI 이미지 생성
```

### 2.2 단순 아키텍처를 선택한 근거

#### A. 트래픽 규모 분석

| 지표 | 추정값 |
|------|--------|
| 발표 시연 동시 사용자 | 10명 미만 |
| 졸업 평가 전체 일일 호출 | < 500 RPS 일일 누적 |
| 글로벌 사용자 | 없음 (한국 평가자만) |
| 이미지 조회 트래픽 | 발표 데모용 ~수백 회 |

→ 이 규모에서 CloudFront/Lambda 도입의 한계 효용은 도입 비용을 초과하지 못함.

#### B. CloudFront를 안 쓴 이유

**CloudFront가 효과적인 경우**:
- 글로벌 사용자 분산 (지역별 엣지 활용)
- 동일 이미지 다회 조회 (캐시 hit rate ↑)
- 일일 GB 단위 트래픽 (S3 직접 요청 비용 절감)

**우리 상황**:
- ❌ 글로벌 분산 X
- ❌ AI 생성 이미지는 사용자별 고유 — 캐시 hit 거의 0
- ❌ 트래픽 작음 → 비용 절감 효과 미미

**추가 도입 비용**:
- 도메인 구입/관리 ($10/년)
- SSL 인증서 (AWS Certificate Manager 무료지만 설정 시간)
- 캐시 무효화 로직 (수정된 이미지 반영 지연 처리)

→ **결론**: ROI 음수. **DAU 5,000+ 또는 글로벌 확장 시점에 도입 검토**.

#### C. Lambda 이미지 리사이징을 안 쓴 이유

**Lambda가 효과적인 경우**:
- 사용자 업로드 이미지를 다양한 해상도로 변환 (썸네일, 미리보기 등)
- EC2 처리 부하가 측정 가능한 수준으로 큼

**우리 상황**:
- ✅ Gemini가 적정 해상도(1024×1024)로 결과 반환 → 추가 리사이징 불필요
- ✅ 사용자 업로드는 base64 → 즉시 S3 직행 (변환 단계 없음)
- ❌ 갤러리 썸네일/미리보기 기능 부재 → 다중 해상도 필요 없음
- ❌ EC2 CPU 사용량이 평균 < 20% → 부하 분산 의미 없음

→ **결론**: 해결할 문제가 부재. **갤러리에 썸네일 도입 시 같이 검토**.

#### D. 단일 EC2 인스턴스 (이중화 없음)

**선택**: t3.small × 1대
**대안**: ALB + Auto Scaling Group (2대 이상)

**유지 근거**:
- 다운타임 SLA 요구 없음 (발표 시연 30분만 가용하면 됨)
- 트래픽이 단일 인스턴스 한계 (~100 RPS)에 도달하지 않음
- 비용: 단일 $19/월 vs ALB+ASG $50+/월

**확장 시점**: DAU 1,000+ 또는 결제 트래픽 상시 발생 시.

### 2.3 단계별 확장 로드맵 (미래 계획)

| 단계 | 트리거 조건 | 도입 기술 | 효과 |
|------|------------|----------|------|
| 0 (현재) | < 100 DAU | EC2 + S3 | 단순, 비용 최소 |
| 1 | 1,000 DAU | + CloudFront | 이미지 응답 속도 ↑, S3 비용 ↓ |
| 2 | 5,000 DAU | + Lambda(썸네일) + RDS Multi-AZ | 부하 분산, DB 가용성 ↑ |
| 3 | 50,000 DAU | + ALB + ASG + ElastiCache | 수평 확장, 캐시 분리 |
| 4 | 글로벌 진출 | + Multi-region S3 + Route53 Geo-routing | 글로벌 지연 시간 ↓ |

### 2.4 면접/발표 예상 질문 & 답변

**Q. 왜 CloudFront 안 썼나?**
A. 트래픽 규모 분석 결과, 글로벌 분산이 없고 AI 생성 이미지가 사용자별 고유라 캐시 hit rate가 0에 가까웠습니다. 도입 비용(도메인, SSL, 캐시 무효화 로직) 대비 한계 효용이 낮다고 판단해 단순 아키텍처를 유지하되, DAU 1,000 도달 시점에 1순위 도입 예정입니다.

**Q. 단일 인스턴스라 다운되면?**
A. 졸업작품 시연 환경 기준 단일 인스턴스로 충분하며, 실제 운영 시 ALB + 최소 2대 ASG로 확장 계획입니다. 현재도 Docker Compose 기반이라 인스턴스 교체 시 5분 내 복구 가능합니다.

**Q. DB가 EC2와 한 컨테이너에서 도는 게 정상인가?**
A. 졸업작품 비용 절감을 위한 단일 인스턴스 구성입니다. 데이터 양이 < 1GB 수준이라 분리 효과가 미미했습니다. 트래픽이 늘면 RDS 분리 → Multi-AZ → 읽기 복제본 순서로 확장.

## 3. 부하 테스트 결과

### 3.1 테스트 도구 선택

**k6** 선택 이유:
- JavaScript 기반 시나리오 작성 — Postman/JMeter보다 코드 친화적
- Cloud 버전 없이 단일 바이너리로 실행 가능
- 리포트 자동 생성 (HTML, JSON)

대안 비교:
- JMeter: GUI 기반, 학습곡선 ↑, JVM 자원 무거움
- Locust: Python 기반, k6보다 syntax 복잡
- Artillery: Node.js — k6보다 리포트 단순
